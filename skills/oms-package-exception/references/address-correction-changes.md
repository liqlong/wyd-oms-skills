# 修改或删除已有地址更正工单

只在用户要求修改或删除已有地址更正工单时读取。创建、提交和状态映射仍见 [工单说明](work-orders.md)。
包裹拦截或调查工单的修改、删除使用 [对应流程](package-changes.md)，不混用地址更正字段。

## 核对当前单据

先查看对应操作的 `describe_oms_package_exception_operation`，再通过 `query_oms` 的
`csc_address_correction_page_query` 按服务工单号精确查询：`orderNoType4ExactMatch=5`，
`orderNoList4ExactMatch` 为实际服务工单号数组，页码和大小按定义。
用户只给业务订单号或跟踪号时先查候选，展示服务工单号、关联订单、状态、当前改址资料及附件；
多单匹配时由用户选定，不把业务订单号或跟踪号直接当作服务工单号。

未查到、已删除或查询失败时停止，不换创建接口实现修改，不重新创建已删除工单。
服务端在当前客户认证范围内重新查单；修改、删除允许的具体业务状态由OMS校验，
不假定所有状态都可操作，也不套用“草稿提交仅允许状态1”的规则。

## 修改

1. 收集用户期望的新收件信息，按定义补齐地址1、邮编、城市、州/省；
   未指定的姓名、电话、国家等字段不猜测补齐或清空。展示当前值与拟提交内容，
   需要沿用已有字段时明确列出供用户确认，不将修改接口当作任意字段的局部补丁。
   用户明确要求清空可选地址字段时可传空字符串；必填地址字段不能清空。
2. 修改附件允许省略或传0至5个，不要求重新上传至少一个附件。
   用户要求替换或新增实际文件时在本Skill内上传，并核对完整拟提交附件清单；
   不擅自删去已有附件，不把省略附件或空列表当作已经确认的清空结果。
   用户明确要求传空列表时使用 `orderFileList: []`，具体效果以OMS回执和后续查询核实。
3. 必须明确 `submitFlag`：1仅保存修改、2修改并提交，无工具默认值。
   用户只要求修改或保存时使用1；明确要求修改并提交时使用2。
   展示真实服务工单号、新地址、附件处理及保存/提交方式，沿用用户对本次具体操作的明确授权。
4. 调用 `update_oms_address_correction(request, confirmed: true)`；请求含实际 `serviceOrderNo`、
   `orderAddressee`、明确的 `submitFlag`，附件按用户指令填写。
   不传业务订单清单、客户身份、旧主单ID或创建操作名称；不自动调用草稿提交工具二次提交。

`SUCCESS` 表示修改或修改并提交的接口成功，不代表承运商已更正地址。
回执包含服务工单号及本次保存/提交方式；可按需查询最新地址、附件和状态。

## 删除

展示确切服务工单号、关联订单及当前状态，核对用户明确要求删除该工单。
已有明确的删除授权不重复询问；“查一下”“重新整理”“继续”或先前建单授权不能当作删除授权。
调用 `delete_oms_address_correction(serviceOrderNo, confirmed: true)`，一次一个用户选定的服务工单号。
删除调用不需要新地址或附件，不额外删除业务订单、上传文件或另建新工单。

`SUCCESS` 表示OMS确认本次工单删除成功，允许 `data` 为空，展示真实服务工单号。
`ERROR` 展示实际原因，不绕过状态校验或改用其他类型删除接口。

## 结果未确认

`UNKNOWN` 不自动重发修改或删除，也不先删除再创建。
修改后按服务工单号核对实际地址、附件和状态，保留尚未核实项；
删除后查看最新状态，单凭查询为空不能确定本次删除成功，不宣称业务订单或原始文件已删除。
无法确定时说明限制并由用户或维护人员进一步核实。
